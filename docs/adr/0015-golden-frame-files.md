# 0015. Golden-frame files

- **Status:** accepted
- **Date:** 2026-11-18
- **Confidence:** medium

## Context

QA-01 layer 3 checks the approved test ROMs (ADR 0014) and the own test cartridges (ADR 0013) against golden frame hashes, and FND-02 asks that CI compare them on Linux, macOS and Windows. The technical design places the goldens in `tests/assets/golden/` as text files, rewritten by `cargo xtask golden --update` and reviewed in the PR diff (sections 6 and 13). Each golden is blessed by hand against an oracle's output and marked unverified until the M8 harness confirms it (QA-01). That needs a file format, a way to drive a ROM to a frame before movies exist (M4), a defined frame hash, and a PNG of a frame to put beside the oracle's. The frame geometry itself (widths, heights, interlace) is decided with the PPU in #89.

## Sources

- FSD QA-01 layer 3 (golden frame hashes; manual blessing, unverified until M8) and FND-02 (per-frame hashes compared on three platforms).
- FSD QA-02 and PROV-05: oracle outputs are stored with the oracle's name and version.
- Technical design section 6 (BLAKE3 for hashes; goldens under `tests/assets/golden/`, regenerated by `cargo xtask golden --update`) and section 13 (golden updates need a written reason; `--update` resets changed entries to unverified).
- `sfes_api::VideoFrame`: width, height and row-major RGB555 pixels as `u16`.
- `anomie-regs#2122`: a CGRAM colour is `-bbbbbgg gggrrrrr`, red in the low bits.
- ADR 0003: `xtask/layers.toml` declares every edge between workspace crates.

## Decision

- **One TOML file per ROM** at `tests/assets/golden/<name>.toml`, covered by one `own` directory entry in the asset manifest:

  ```toml
  rom = "fetched/krom/RotZoom.sfc"   # relative to tests/assets/
  rom_sha256 = "…"

  [[input]]                          # optional; held from `frame` until the port's next entry
  frame = 30
  port = 0
  buttons = "START"                  # sfes_api::Buttons flag names, "A | B"; "" releases all

  [[checkpoint]]
  frame = 60
  width = 256
  height = 224
  blake3 = "…"
  status = "unverified"              # or "oracle-confirmed"
  oracle = "MesenCE <version>"       # with `blessed`, absent until a person blesses the entry
  blessed = "2026-11-18"
  ```

- **Frames are counted from 1**: frame *n* is the *n*-th frame the machine renders after power-on with seed 0, and input entries for frame *n* are applied before it runs. Inputs and checkpoints are listed in increasing frame order, at most one input entry per port and frame. The input script is a stopgap until movies arrive in M4 and is then replaced by a movie file.
- **Frame hash:** BLAKE3 of the frame's pixels, each `u16` written little-endian, row-major, as 64 lower-case hex digits; width and height are recorded separately. The hash covers exactly the `VideoFrame` the machine returns, so what it contains for hi-res and interlaced modes is #89's decision, not this one.
- **Status:** `unverified` until the M8 harness upgrades an entry to `oracle-confirmed`, which requires `oracle`. A person blesses an `unverified` entry after comparing the frame with the oracle's by adding `oracle` and `blessed`. `oracle` and `blessed` come together or not at all.
- **Runner:** `sfes_test_harness::golden` parses and validates files, drives a `FrameMachine` (set buttons, run one frame) through the input script, compares checkpoints and, for `--update`, rewrites changed checkpoints and resets each one to `unverified` with no `oracle` or `blessed`. `golden::boot` is the one place the machine is wired in: it builds a `Snes` with seed 0 (#79, ADR 0018).
- **Commands:** `cargo xtask golden --update [<name>…]` reruns the named goldens, or all of them, and rewrites them. `cargo xtask golden --png <name> <frame>` runs a golden's ROM and input script to `frame` and writes `target/golden/<name>-<frame>.png`. The PNG expands each 5-bit channel to 8 bits by repeating its top bits (`c << 3 | c >> 2`) and reads red from the low bits as CGRAM stores it; it is for visual comparison only and never hashed.
- **Dependencies:** the harness gains `blake3`, `sha2` (to check `rom_sha256`) and `toml`; xtask gains `png` (MIT OR Apache-2.0) and a dependency on `sfes-test-harness`, declared in `xtask/layers.toml`, so `golden --update` runs the same code as the tests.
- **Reviews:** a PR that changes a golden says why in a "Golden changes" section of its description.

## Consequences

- A golden needs no running machine to be checked for form, so the format and its tooling land before #79; the harness checks every committed golden file's form on each push.
- `xtask` now builds the chip crates through the harness, which lengthens a cold `cargo xtask` build.
- If #89 decides that `VideoFrame` pixels are not in CGRAM's bit order, the PNG writer changes with it; the hashes do not.
- When movies arrive in M4 the `[[input]]` tables are converted to movie files and the format gains a version.
